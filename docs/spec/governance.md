## 1. 规范文档层级与裁决规则

| 层级 | 位置 | 定位 | 权威性 |
| --- | --- | --- | --- |
| 根目录总规范入口 | [SPEC.md](../../SPEC.md) | 核心架构铁律、分模块规范目录与 RFC 总入口 | **最高** |
| 分模块工程规范 | `docs/spec/*.md` | 当前生效的硬性工程规则与边界 | **最高**（与 `SPEC.md` 共同构成生效 SPEC） |
| 独立设计提案 | `rfcs/NNNN-*.md` | 设计背景、备选方案对比、决策依据与阶段拆解 | 背景与提案；与 SPEC 冲突时**以 SPEC 为准** |
| 开发实施规范 | `docs/development/*.md` | 具体子系统的代码落点、实施步骤与验收手册 | 实施指导；不得突破 SPEC 边界 |
| Agent 运行时指南 | `docs/agent/*.md` | `kite docs` 与 MCP/Skill 暴露给运行中 Agent 的精简操作手册 | 单一事实来源；不掺杂内部架构细节 |

硬性裁决规则：

- 已采纳的 RFC 若未同步更新至 `SPEC.md` / `docs/spec/`，视为**尚未生效**。
- 代码评审以 `SPEC.md` 与 `docs/spec/` 为准；与规范冲突的代码，必须修改代码或按流程先走 RFC 修订规范。
- 仅作措辞修正、补充示例、修正过期路径或整理索引而不改变规则的改动，可直接更新规范文档，不需要新增 RFC。

## 2. RFC 编写与生命周期

### 2.1 必须先写 RFC 的变更

满足以下任一条件时，**必须**先在 [rfcs/](../../rfcs/README.md) 提交 RFC：

1. 新增或拆分 Rust crate、Bun package，或调整内部依赖方向。
2. 改变 Rust 与原生界面的职责边界，或调整命令/状态/媒体三条通道机制。
3. 引入新的外部协议、网络入口、主机侧依赖，或替换核心第三方依赖（如 SSH 库、串流库）。
4. 引入跨多个里程碑或跨平台的交互/协作模型变更。

修 bug、在现有规则内补全功能或重构内部实现，不需要单独写 RFC。

### 2.2 编号与状态流转

- 文件命名：`rfcs/NNNN-短标题.md`（四位递增编号，不复用）。从 [rfcs/0000-template.md](../../rfcs/0000-template.md) 复制起草。
- 历史注记：`0027` 与 `0028` 在早期并行分支中各存在两份历史文件（已保留原文件名避免断链）；自 `0033` 起严格唯一递增，不得再出现重号。
- 状态集合：`草案` → `讨论中` → `已采纳`（同次提交同步 SPEC）→ `已实现`（代码与验收落地）；未采纳标为 `已拒绝`，被新设计替代标为 `已被取代` 并在文首注明替代编号。
- 已采纳的 RFC 不再推倒重写；需推翻或大幅调整时新增 RFC 并将旧 RFC 标记为 `已被取代`。

## 3. 兼容面与分级验收基线

- **重构兼容面**：不默认叠加旧接口兼容壳。FFI 绑定与库始终同次构建，不保留废弃 FFI 入口；上游 `herdr 0.9.5` 协议、已保存的主机信任指纹、设备私钥材料、provider 原始历史文件与既有用户数据格式必须安全保留或幂等迁移。
- **分级证据纪律**：验收记录必须严格区分以下四类不同层级的证据，**不得互相替代**：
  1. **静态与离线检查**：类型检查、lint、依赖边界检查、Rust/Bun 单测。
  2. **协议与夹具验收**：进程内 SSH/模型/ACP 夹具回归。
  3. **真实模型与主机联调**：真实 provider owner、真实工具输出（不以模型自述代替真实工具返回）与真实断线恢复。
  4. **原生设备与正式包验证**：真实设备/受控 UI 帧稳定性、实际视频解码呈现、输入到达以及由 GitHub 标签 CI 产出的正式 Release 包。
- **发布交付纪律**：正式版 `vX.Y.Z` 与预发布版 `vX.Y.Z-alpha.N` 必须由 GitHub `Publish Release` 标签 CI 构建并发布至 GitHub Release；签名材料与设备私钥严禁进入源码、附件或日志。详见 [docs/releases.md](../releases.md)。
