# RFC 0020：闲置会话进程回收与按需恢复

> 编号：0020 · 状态：已实现 · 创建：2026-11-02
> 相关：RFC 0007（修订归档后的进程生命周期）、RFC 0014、RFC 0018

## 背景

归档目前只修改会话索引，完成的 Codex TUI、独立 app-server 和 MCP 子进程仍然驻留。wen.linux 的 15 个已归档会话回收后，物理内存用量由约 18 GiB 降到约 8 GiB。用户要求会话一小时无活动即可释放进程，再次使用时从原上下文恢复。

## 目标

- 已归档会话在任务结束、上下文落盘后释放运行进程。
- 未归档会话闲置满一小时后释放运行进程；状态轮询、账户查询和连接保活不延长期限。
- 保留 provider thread、完整历史、会话记录和可复用的 shell pane。继续会话使用原 thread ID。

## 设计

`kite-app::host_node::lifecycle` 在主机独立运行，每 30 秒检查一次。Rust 决定归档回收和一小时闲置规则；Linux Python 辅助程序提供进程、线程状态和文件事实，并执行持租约的退出。

活动时间取显式继续/恢复时间、owner 启动时间和原始 provider 历史的修改时间。普通发现和只读 RPC 不更新活动时间。检查实际 app-server 的全部已加载线程，并结合 Herdr 识别的前台进程；执行中、等待审批、暂停、未知、未落盘和共享 owner 均保留。

执行回收时复用 `session-open` 的会话锁和 owner 锁，再次核对目录记录、provider 引用、PID/start ticks、活动指纹和实时空闲状态。先向核验过的闲置 TUI 发送 SIGTERM，再次检查 owner，最后向独立 app-server 进程组发送 SIGTERM。暂停的 TUI 保留。退出通过进程信号执行，避免把 `/quit` 拼进未提交的输入草稿。只退出远程 TUI 不会释放其持久 app-server，因此必须执行两步。回收不删除 provider 文件，不改变归档状态，不重放消息或工具操作。

Node `status.sessionLifecycle` 暴露固定期限、扫描间隔、最近成功扫描时间和回收数量。升级与扫描共用 observation gate，旧代次进入 draining 后不再执行回收。

## 备选方案

仅关闭客户端不能释放持久 owner。归档时直接终止任务会丢失正在执行的工作。按状态轮询时间保活会使连接中的闲置会话永不过期。

## 对 SPEC 的影响

归档继续保留正在运行的任务；增加任务结束后的回收，以及未归档会话一小时闲置回收。原始历史和按原 thread 恢复的要求保持适用。

## 验证

覆盖一小时时间边界、只读轮询、重新活动、进行中的后台线程、未落盘上下文、PID 复用、并发解除归档、共享 owner、TUI 断开后的新活动，以及回收后原 thread 的恢复。主机升级使用现有兼容热交接流程。
