# RFC 0002：iOS 支持，以及 iPhone 与 iPad 的区分适配

> 编号：0002 · 状态：已采纳 · 创建：2026-10-28
> 相关：RFC 0001（原计划在 M7 做 iOS，本 RFC 把它提前）

## 背景

RFC 0001 把 iOS 排在最后一个里程碑（M7）。现在 Android 端卡在 SDK 下载上，而本机已经有 Xcode 16.4 和 iOS 18.5 SDK，所以先把 iOS 补到和 Android 相同的 M1 水平。

iPhone 和 iPad 的屏幕、输入方式和多任务能力差别很大，不能一套布局硬套，需要先定下适配原则。

## 目标

- iOS App 达到 M1：生成并安全保存本机密钥，通过 SSH 连上主机，执行 `herdr remote-api-bridge --check`。
- 一个通用 App 同时支持 iPhone 和 iPad，两者的布局分别优化。
- 和 Android 共用同一个 Rust 内核，通过 kite-ffi 和 UniFFI 生成的 Swift 绑定接入。

**不做的事：**

- Mac Catalyst、visionOS。
- 后台保持 SSH 连接（iOS 不允许，后台通知方案见 RFC 0001 第 10 节）。
- Intel Mac 上的模拟器（`x86_64-apple-ios`），以后有需要再加。

## 设计

### 工程

- 目录 `ios/`，用 XcodeGen 的 `project.yml` 描述工程。生成的 `Kite.xcodeproj` 不提交，执行 `xcodegen generate` 生成。
- App target 名 `Kite`，bundle id `io.github.wenshiqi0.kite`，与 Android 的 applicationId 一致。最低支持 iOS 17（为了用 Observation 框架的 `@Observable`）。
- 设备族同时包含 iPhone 和 iPad（`TARGETED_DEVICE_FAMILY = 1,2`），iPad 支持全部方向和多窗口。

### Rust 内核接入

- iOS 链接 `kite-ffi` 的静态库。构建脚本用 `cargo rustc --crate-type staticlib` 临时指定库类型，`Cargo.toml` 里仍然只声明 cdylib。这样 Android 构建不会多编一份静态库（release 下还会多做一次 LTO）。
- Rust 编译目标：真机 `aarch64-apple-ios`，Apple Silicon 模拟器 `aarch64-apple-ios-sim`。
- `ios/scripts/build-rust.sh` 作为 Xcode 的编译前脚本：
  - 根据 Xcode 传入的 `PLATFORM_NAME` 选择 Rust 目标，Debug 配置用 dev profile，Release 配置用 release profile。
  - 只编译当前目标平台，把 `libkite_ffi.a` 放到 `ios/build/rust/<平台>/`。
  - 用 uniffi-bindgen 生成 Swift 绑定，放到 `ios/Generated/`（不提交）：Swift 文件编进 App target，C 头文件和 module map 放在 `ios/Generated/include/`，供 Swift 以 `kite_ffiFFI` 模块导入。
- 以后加入 Widget、分享扩展等多个 target 时，再改成 XCFramework 加本地 Swift Package。

### 代码结构

```
ios/
├── project.yml
├── scripts/build-rust.sh
└── Kite/
    ├── App/          入口（KiteApp）
    ├── UI/           SwiftUI 视图和 ViewModel（@Observable）
    ├── Data/         平台存储适配：Keychain、UserDefaults
    └── Resources/    Localizable.xcstrings、资源目录
```

- ViewModel 的职责和 Android 一样：把 Rust 的结果转成界面状态、把用户操作转成 Rust 调用、选择文案。
- 私钥存进 Keychain（`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`，不同步到 iCloud），作用等同于 Android 上用 Keystore 加密。
- 文案只写在 `Localizable.xcstrings` 里，代码里用语义化的 key。

### iPhone 与 iPad 的适配原则

**布局由尺寸类别（size class）和可用宽度决定，不由设备型号决定。** iPad 在分屏（Split View）、侧拉（Slide Over）或者台前调度的小窗口里，宽度会变成紧凑（compact），这时必须使用 iPhone 的布局。设备型号只用来判断能力：是否支持多窗口、指针、硬件键盘快捷键。

| 维度 | 紧凑宽度（iPhone，以及 iPad 的窄窗口） | 常规宽度（iPad 全屏或宽窗口） |
|---|---|---|
| 导航 | `NavigationStack`：agent 列表 → 聊天 | `NavigationSplitView`：左栏是按主机分组的 agent 列表，右侧是聊天 |
| 远程桌面 | 与 Android 手机一致：浮窗、上下分屏、全屏、画中画 | 默认左右并排：一侧聊天、一侧桌面，分隔线可拖动；也能切到浮窗、全屏、画中画 |
| 方向 | 竖屏为主；横过来进入全屏桌面 | 任何方向都用并排布局，不靠旋转切换模式 |
| 键盘 | 软键盘加快捷键栏 | 支持硬件键盘：⌘↩ 发送，⌘1–⌘9 切换 agent；接管时把按键转发到远程桌面。系统保留的组合键（⌘Tab、⌘Space 等）无法转发 |
| 指针 | 不考虑 | 支持触控板和鼠标：悬停效果；接管远程桌面时请求指针锁定（`prefersPointerLocked`），拿到相对移动 |
| 多窗口 | 单窗口 | 支持多个窗口：例如一个窗口看 agent A 的聊天，另一个窗口全屏看桌面 |
| M1 骨架 | 单列：本机密钥、主机表单、检查结果依次排列 | 两列：左列是本机密钥和主机表单，右列是检查结果 |

外接硬件键盘和指针在 iPhone 上也可能出现，所以键盘快捷键和指针支持按"是否连接"判断，不按设备型号判断。

### 里程碑

iOS 的 M1 在本 RFC 中完成。从 M2 开始，每个里程碑尽量同时交付 Android 和 iOS；同一功能在 iPhone 和 iPad 上的布局差异写在对应功能的 RFC 里。

## 备选方案

- **手写 `.xcodeproj`**：pbxproj 格式难以手写和审阅，合并时容易冲突。XcodeGen 的 YAML 描述更清楚。
- **XCFramework 加本地 Swift Package**：多 target 时更合适，但每次构建都要同时编译真机和模拟器两个目标，现在只有一个 App target，先用更简单的直接链接方式。
- **按设备型号分别做 iPhone 和 iPad 界面**：iPad 的窄窗口会用错布局，所以不采用。

## 对 SPEC 的影响

- 第 2 节：写明 `ios/` 的结构和生成物位置。
- 第 3 节：`kite-ffi` 是唯一对外的库，Android 用 cdylib，iOS 用 staticlib。
- 第 5 节：增加 iOS 约定，以及 iPhone / iPad 适配规则。
- 第 6 节：M1 的差距同样适用于 iOS。
